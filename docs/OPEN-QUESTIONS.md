# OPEN QUESTIONS — P0-S0 Schema Freeze

Ambiguities found in the architecture spec that Builder A resolved locally and now defers to Commander. None block S0; each may require a schema_version bump if ruled differently.

| # | Question | Spec ambiguity | Builder A's provisional resolution | Impact if reversed |
|---|----------|----------------|------------------------------------|--------------------|
| OQ-1 | Which canonicalization standard does §6.1 intend? | Doc says "字段顺序、数值格式和 Unicode 归一化必须固定" without naming a standard | JCS/RFC 8785 minus floats (UTF-16 key sort, NFC, integers only) — ADR-S0-001 | Re-freeze all golden vectors |
| OQ-2 | `EvidenceArtifact.content_hash` — payload hash or object self-digest? | §6 lists `content_hash` in the artifact's own field list (payload semantics), while §6.1 uses `content_hash` as the universal self-digest | Renamed payload field to `payload_hash`; `content_hash` reserved for self-digest — ADR-S0-003 | Rename back / split naming; vector regen |
| OQ-3 | Should object-ID uniqueness (e.g., duplicate `artifact_id`, duplicate `criterion_id`) be schema-enforced? | "duplicate IDs" test requirement is checkable intra-object (criterion_id within success_criteria) but cross-object uniqueness is a storage concern | Schema enforces intra-object duplicates only (bundle artifact_hashes); cross-object uniqueness left to persistence layer | Add schema-level rules if Commander wants uniqueness inside IntentContract too (e.g., no duplicate criterion_id — **currently not enforced**, flagged) |
| OQ-4 | Are `state`/`status` fields part of the hash preimage for the six objects? | §6 field lists omit state for most objects; §7 defines state machines whose transitions would mutate the hashed object if `state` were inside | S0 includes `state` ONLY on EvidenceBundle (OPEN/SEALED drives data invariants); other objects hash without lifecycle fields — S1 concern | Field set changes → new vectors |
| OQ-5 | SubjectRef grammar — is `<kind>:<id>` with kinds {user,org,agent,verifier,arbitrator,service,operator} and `@` allowed in id the intended form? | §13 defines identity categories but no wire format | Adopted `<kind>:<id>`; `@` permitted for `verifier:x@1` — ADR-S0-003 | Regex change → new vectors |
| OQ-6 | Signature schemes — is the enum {ed25519, secp256k1, eip191, eip712, passkey-p256} sufficient/correct? | Spec requires signatures (§6, §8.3) but defines no scheme registry | Provisional enum; extendable only via new schema_version | Enum membership change → new version |
| OQ-7 | AssetRef format — `{network, asset, decimals}` vs CAIP-19? | §6/附录A says `AssetRef` without format; P0 forbids mainnet, chain adapter comes later | `{network:"evm:8453"|"fiat:USD"|"sim:local", asset, decimals}` — CAIP-2-flavored network id | Ref change → new version |
| OQ-8 | Decimal precision bounds | Decimal strings are format-checked but unbounded | No max scale enforced (asset.decimals exists for interpretation) | Add scale/precision rule if ruled |
| OQ-9 | Should `change_reason`/`signature` be mandatory at freeze time rather than optional in schema? | §7 FreezeIntent says "签名失败则保持 DRAFT" — schema allows unsigned objects | Schema permits unsigned (draft transport); freeze-time signature requirement is a *workflow* rule, S1 | If freeze-time must be schema-encoded: add `FROZEN` variant type |
